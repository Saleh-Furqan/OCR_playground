# 6. Security and Authentication

## 6.1 Client Certificate Authentication

Client certificate authentication provides strong device-based authentication using mutual TLS where both the client and server present certificates during the SSL handshake. This approach eliminates many vulnerabilities associated with password-based authentication including credential theft through phishing, brute force attacks attempting many passwords, and password reuse across services. Each device receives a unique cryptographic certificate that serves as its identity, and the private key associated with the certificate never leaves the device ensuring it cannot be intercepted during transmission.

The authentication flow begins when a user requests a certificate from the ReTouch Certificate Authority. The user accesses the CA portal at retouchhk.com/certmanage and authenticates using a traditional username and password. This initial authentication bootstraps the device registration process. Once authenticated, the user generates a Certificate Signing Request on their device which contains their public key and identifying information like device name. The CSR is submitted to the CA portal where it is validated and signed with the CA's private key creating a certificate valid for one year.

The issued certificate is returned to the user and installed in their browser's certificate store or operating system keychain. Modern browsers provide certificate management interfaces where users can import certificates in PKCS12 or PEM format. On mobile devices, certificates can be installed through configuration profiles on iOS or directly through settings on Android. Once installed, the certificate is available for presentation during TLS handshakes with websites that request client certificates.

When the user subsequently visits the ReTouch application and attempts to access API endpoints, the browser initiates an HTTPS connection to nginx. During the TLS handshake, nginx's configuration specifies that client certificates are optional using ssl_verify_client optional. The browser checks its certificate store for certificates issued by a CA that nginx trusts, finds the ReTouch certificate, and presents it as part of the handshake. Nginx verifies the certificate by checking the signature using the CA's public key, verifying the certificate has not expired, and ensuring the certificate chain is valid. If verification succeeds, nginx sets environment variables including $ssl_client_verify with value SUCCESS and $ssl_client_s_dn containing the subject distinguished name from the certificate. These variables are passed to upstream services through proxy headers.

The backend extracts the device identifier from the subject distinguished name, specifically from the Common Name field which contains the device ID assigned during certificate issuance. This device ID is used for all authorization decisions including verifying that receipt access requests match the owning device. The device ID is considered trusted since it comes from a cryptographically verified certificate that was issued by the ReTouch CA and cannot be forged without access to the CA's private key.

## 6.2 Certificate Authority Implementation

The Certificate Authority is implemented as a separate Flask application in the retouch-ca directory. Separating the CA from the main application provides security isolation ensuring that compromise of the main application does not automatically compromise the CA's private key. The CA has its own database for storing user accounts and certificate issuance records, and runs on a different port with different rate limiting rules.

The CA's own certificate and private key were generated during initial system setup using OpenSSL commands. The CA certificate is self-signed since it is the root of trust for the ReTouch ecosystem and does not need validation from external certificate authorities. The private key is stored securely with restrictive file system permissions ensuring only the CA process can read it. The public certificate is distributed to nginx and configured as the ssl_client_certificate ensuring nginx trusts certificates issued by this CA.

Certificate issuance uses the Python cryptography library which provides high-level APIs for generating X.509 certificates. When processing a CSR, the CA parses the request to extract the public key and subject information, validates that the subject includes required fields like Common Name, generates a unique serial number for the certificate using random bytes ensuring each certificate can be uniquely identified, sets the validity period typically one year from issuance with notBefore and notAfter dates, adds the device ID to the Common Name field linking the certificate to a specific device record, signs the certificate using the CA's private key and SHA-256 hashing algorithm, and stores the certificate record in the CA database for revocation checking.

The issued certificate is returned to the user in PEM format which is text-based and can be copied and pasted or downloaded as a file. The PEM format includes the certificate in base64 encoding between BEGIN CERTIFICATE and END CERTIFICATE markers. Users can import this directly into browsers or convert it to PKCS12 format using OpenSSL if their platform requires it.

Certificate revocation is supported through a simple database field tracking certificate status. When a certificate needs to be revoked because a device was lost or compromised, an administrator can mark the certificate as revoked in the CA database. However, nginx currently does not check revocation status on each request which would require implementing Certificate Revocation Lists or Online Certificate Status Protocol. This limitation is acceptable for the current scale but should be addressed before production deployment at scale.

## 6.3 Transport Layer Security

All traffic between clients and the server is encrypted using HTTPS with TLS 1.2 or TLS 1.3 protocols. TLS encrypts data in transit preventing eavesdropping and man-in-the-middle attacks where attackers intercept and potentially modify traffic. The nginx configuration specifies strong cipher suites prioritizing perfect forward secrecy through ECDHE key exchange algorithms. Perfect forward secrecy ensures that even if the server's private key is compromised in the future, previously recorded encrypted sessions cannot be decrypted.

The server certificate for the retouchhk.com domain is issued by Let's Encrypt which is trusted by all major browsers. This eliminates browser warnings that would appear with self-signed certificates and provides users with confidence they are connecting to the legitimate ReTouch service. The Let's Encrypt certificate verifies the server's identity but does not verify clients, which is why client certificates are needed for device authentication.

HSTS or HTTP Strict Transport Security headers instruct browsers to always use HTTPS when connecting to ReTouch even if the user types http in the address bar. This prevents protocol downgrade attacks where an attacker forces the connection to use unencrypted HTTP allowing traffic interception. The HSTS policy is set with a max-age of one year and includes subdomains ensuring all ReTouch services benefit from the protection.

## 6.4 Input Validation and Sanitization

Input validation occurs at multiple layers preventing injection attacks and data corruption. The frontend validates user input before submission checking file types to ensure only images and PDFs are uploaded, verifying file sizes do not exceed the 10MB limit, and ensuring required fields are provided before enabling the submit button. While client-side validation improves user experience by providing immediate feedback, it cannot be relied upon for security since it can be bypassed by manipulating browser developer tools or making direct API requests.

The backend validates all inputs using Marshmallow schemas which define expected data types, required fields, and validation rules. Schema validation occurs automatically through Flask-Smorest before route handlers execute ensuring handlers only process well-formed data. String fields have maximum length constraints preventing excessively long inputs that could cause buffer overflows or database errors. UUID fields are validated to ensure they match the expected format preventing malformed IDs from causing database lookup failures.

The backend also performs business logic validation beyond data type checking. When a receipt access request arrives, the backend verifies the device ID from the client certificate matches the device ID that owns the requested receipt. This prevents horizontal privilege escalation where one user accesses another user's data. Database queries use parameterized queries through SQLAlchemy's ORM which automatically escapes parameters preventing SQL injection attacks where attackers insert malicious SQL code through input fields.

File uploads are validated to ensure they match expected MIME types. The backend checks the Content-Type header and can also inspect file contents using libraries like python-magic to verify the actual file format matches the declared type. This prevents upload of executable files disguised as images that could be used for attacks if the file storage were misconfigured to allow execution.

## 6.5 Rate Limiting and Abuse Prevention

Rate limiting prevents abuse including brute force attacks attempting many authentication tries, denial of service attacks overwhelming the server with requests, and scraping where automated tools extract large amounts of data. Nginx implements rate limiting using the limit_req_zone and limit_req directives which track request rates per client IP address.

The API rate limit allows 300 requests per minute per IP which is sufficient for normal usage including uploading multiple receipts or viewing many receipts in quick succession, but prevents automated tools from making thousands of requests. The burst parameter allows short-term spikes above the rate limit absorbing legitimate traffic bursts without rejecting requests. If a client exceeds the rate limit including the burst allowance, nginx returns a 429 Too Many Requests status code indicating the client should slow down.

The Certificate Authority portal has a more restrictive rate limit of 30 requests per minute since certificate issuance should be infrequent. Most users will request one certificate per device and certificates are valid for one year, so there is little legitimate need for frequent CA access. The stricter limit prevents automated certificate generation that could be used to create many fake devices for abuse.

Rate limiting uses shared memory zones that are maintained across nginx worker processes ensuring limits are enforced consistently. The zones are keyed by client IP address so each IP has its own independent rate limit. This means users on different IPs do not affect each other's limits, but users sharing an IP such as those behind a corporate NAT will share rate limits which could occasionally cause false positives in high-traffic scenarios.

## 6.6 Secure Data Storage

Sensitive data is stored securely at rest and in transit. Database credentials, AWS API keys, and the CA private key are provided through environment variables rather than hardcoded in source files. This follows security best practices preventing accidental exposure of secrets through source code repositories. The docker-compose.yml file contains placeholder environment variables with actual secrets provided through .env files that are excluded from version control using .gitignore.

User passwords for the Certificate Authority portal are hashed using Werkzeug's generate_password_hash function which uses PBKDF2 with SHA-256 by default. Password hashing ensures that even if the database is compromised, attackers cannot immediately use the passwords since they would need to crack the hashes. PBKDF2 includes a salt unique to each password preventing rainbow table attacks, and uses multiple iterations of the hash function to slow down brute force cracking attempts.

Receipt files stored in S3 are not encrypted at rest in the current implementation, relying on AWS's physical security and access controls. S3 supports server-side encryption that could be enabled to automatically encrypt all uploaded files using AWS-managed keys or customer-provided keys. This would provide additional protection if AWS's security were compromised or if misconfigured bucket permissions accidentally exposed files.

Database backups should be encrypted before being stored long-term or transferred offsite. PostgreSQL supports encryption at rest using file system or volume encryption where the entire database directory is encrypted. Backup files can be encrypted using tools like GPG before uploading to archival storage ensuring archived data remains protected.

# 7. Challenges and Solutions

## 7.1 Static File Serving Performance

Early in development, the production deployment served static frontend files by proxying requests from nginx to the Vite development server running in a container. This approach simplified deployment since the same configuration could be used in development and production, but resulted in poor performance. Benchmarking showed that serving a simple JavaScript file through the Vite dev server took 50-100 milliseconds per request with throughput limited to a few hundred requests per second. As the frontend bundle grew, the situation worsened since Vite was processing requests through its module transformation pipeline even though production builds had already been optimized.

The solution involved reconfiguring nginx to serve static files directly from the file system without proxying to the frontend container. The frontend Dockerfile was modified to copy the built dist directory to nginx's webroot directory at /usr/share/nginx/html. The nginx configuration was updated to use the root directive pointing to this directory and the try_files directive to implement SPA routing fallback. After these changes, benchmarking showed response times under 1 millisecond and throughput exceeding 40,000 requests per second representing a 40x performance improvement. This change required understanding the difference between development and production serving strategies and recognizing that different configurations were appropriate for each environment.

## 7.2 Database Connection Timing

When deploying with Docker Compose, occasional startup failures occurred where the backend container would start before PostgreSQL was ready to accept connections. The depends_on directive in docker-compose.yml ensures PostgreSQL starts before the backend, but does not wait for PostgreSQL to finish initialization and be ready to accept connections. The backend would attempt to connect to PostgreSQL, fail because the database was still starting, and crash with a connection refused error.

The solution used a wait-for-it.sh script which repeatedly attempts to connect to a specified host and port, sleeping between attempts, until the connection succeeds or a timeout is reached. The backend's entrypoint script was modified to run wait-for-it.sh targeting PostgreSQL's port before starting Gunicorn. This ensured the backend only started after PostgreSQL was ready. The script uses basic networking tools like nc or telnet to test TCP connectivity making it lightweight and portable across different base images. This pattern is widely used in Docker environments and is recommended in Docker Compose best practices.

## 7.3 Docker Networking Confusion

Early Docker networking configuration used localhost to reference services causing connection failures within containers. For example, the backend tried connecting to PostgreSQL at localhost:5432 which failed because inside the backend container, localhost refers to that container itself not the PostgreSQL container. Similarly, nginx tried proxying to http://localhost:5000 which also failed.

Understanding Docker Compose networking resolved this issue. Docker Compose automatically creates a bridge network for all services and configures DNS so containers can reach each other using service names from docker-compose.yml. The backend was reconfigured to connect to postgres:5432 where postgres is the service name, and nginx was configured to proxy to http://backend:5000. These hostnames are resolved by Docker's DNS to the appropriate container IP addresses. This required shifting mental models from traditional server deployment where everything runs on one machine to containerized deployment where each service is isolated.

## 7.4 Certificate Authentication Complexity

Implementing client certificate authentication proved more complex than initially anticipated requiring deep understanding of TLS, X.509 certificates, and PKI concepts. Initial attempts to configure nginx certificate verification failed due to incorrectly formatted CA bundles, misunderstanding of certificate chains, and confusion about client versus server certificates.

Extensive documentation reading and experimentation clarified the concepts. The server certificate proves the server's identity to clients and must be signed by a publicly trusted CA like Let's Encrypt. The client certificate proves the client's identity to the server and must be signed by the ReTouch CA. The CA bundle configured in nginx contains the ReTouch CA's certificate allowing nginx to verify signatures on client certificates. Testing with OpenSSL's s_client command helped verify the server configuration by simulating certificate-based connections and viewing detailed handshake information. Creating thorough documentation of the certificate issuance and installation process ensured team members could obtain certificates without deep PKI knowledge.

## 7.5 S3 Presigned URL Caching

Presigned URLs include expiration timestamps and cryptographic signatures ensuring they can only be used for a limited time. However, aggressive browser caching caused issues where expired presigned URLs were used to attempt downloading receipts resulting in access denied errors. The backend generates presigned URLs valid for one hour, but if a user viewed a receipt and then revisited the same receipt two hours later, the browser would use the cached URL which had expired.

The solution involved setting appropriate cache headers on API responses containing presigned URLs. The Cache-Control header was set to no-store preventing browsers from caching the API response containing the presigned URL. This ensures that each receipt view request fetches a fresh presigned URL from the backend which generates a new URL with current timestamp. The receipt images themselves fetched directly from S3 can still be cached since they do not change, but the URLs used to access them are always fresh. This required understanding HTTP caching semantics and the difference between caching resources versus caching URLs to resources.

## 7.6 SPA Routing with Nginx

Single-page applications use client-side routing where JavaScript code handles navigation without requesting new HTML documents from the server. When a user clicks a link to /receipt/device1/abc123, React Router intercepts the click, updates the browser URL, and renders the appropriate component without making a server request. However, if the user bookmarks this URL and returns later, or shares the URL with someone else, the browser makes a full request to nginx for /receipt/device1/abc123. Without special configuration, nginx would return a 404 Not Found since there is no file at that path.

The solution uses nginx's try_files directive with fallback to index.html. When a request arrives, nginx first checks if a file matching the path exists serving it if found. This handles actual static assets like JavaScript bundles and images. If no file exists, nginx serves index.html instead. The React application then loads and React Router examines the current URL and renders the appropriate component. This configuration enables deep linking where URLs pointing to specific application states work correctly even when loaded directly rather than navigated to from within the application.

## 7.7 Environment Variable Management

Managing environment variables across development, staging, and production environments proved tedious and error-prone. Developers needed different values for database URLs, AWS keys, and API endpoints between environments. Initially, environment variables were hardcoded in docker-compose.yml requiring manual editing when switching environments and creating risk of accidentally committing production secrets to version control.

The solution used Docker Compose's .env file support where environment variables are defined in files named .env which are loaded automatically when docker-compose runs. Separate .env files were created for each environment including .env.development, .env.staging, and .env.production. The active .env file is symlinked or copied to .env before starting containers. The .gitignore file excludes all .env files preventing accidental commits of secrets. A .env.example file with placeholder values is committed to version control serving as documentation of required variables. This pattern is widely used and provides good separation between code and configuration while remaining simple to understand and manage.

# 8. Future Work and Enhancements

## 8.1 OCR Integration

Optical character recognition represents a significant planned enhancement that would extract structured data from receipt images. Users currently upload receipts which are stored as images, but the data within the images including merchant name, date, total amount, and line items remains unstructured. OCR would parse the image extracting key fields and storing them in the database enabling powerful features like searching for receipts by merchant or filtering by date range.

Several OCR services are being evaluated including Google Cloud Vision API which provides excellent accuracy for printed text and handles various receipt formats well, AWS Textract which is already integrated with the AWS ecosystem and could provide cost benefits, and open-source Tesseract which provides adequate accuracy for well-scanned receipts and avoids per-image processing costs. The integration would involve adding an OCR processing step after upload where images are sent to the chosen OCR service, parsing the returned text using regular expressions or machine learning models trained on receipt formats, extracting key fields and normalizing data such as standardizing date formats and parsing currency amounts, and storing extracted data in new database tables including a merchants table and line_items table with foreign keys to receipts.

The OCR results would power new frontend features including a search interface allowing filtering by merchant, date range, or amount range, automatic categorization of spending by merchant or expense type, and visualization showing spending trends over time or breakdown by category. OCR accuracy is not perfect especially for poor quality images or handwritten receipts, so the system would allow manual correction where users could edit extracted data if errors are detected.

## 8.2 Progressive Web App

Transforming the web application into a Progressive Web App would enable offline functionality and mobile app-like experience without requiring separate native iOS and Android applications. PWA features include adding a web app manifest file defining the app name, icons, and display mode allowing the app to be installed to device home screens, implementing a service worker that caches static assets and API responses enabling the app to load and function even without internet connectivity, using IndexedDB for client-side storage allowing receipts to be queued for upload when offline and automatically sync when connectivity returns, and implementing push notifications to alert users about expense report deadlines or unusual spending patterns.

The service worker would implement a cache-first strategy for static assets serving them from cache if available and falling back to network only if not cached. For API requests, a network-first strategy would attempt to fetch from the server but fall back to cached data if the network is unavailable. Background sync would queue failed uploads and retry when connectivity returns. The PWA would feel like a native app with no browser chrome, smooth animations, and instant loading from cache. Users could add the app to their home screens and launch it like any other app while still benefiting from web technologies and automatic updates without app store approval.

## 8.3 NFC Payment Integration

Near Field Communication integration would allow capturing receipt data directly from point-of-sale terminals eliminating the need for paper receipts entirely. Modern payment terminals can transmit transaction details to mobile devices via NFC. The ReTouch mobile PWA or native app would listen for NFC payments, capture transaction details including merchant ID, transaction amount, timestamp, and payment method, automatically create a receipt record with this data, and optionally trigger OCR processing if the merchant provides a receipt image via NFC or related protocol.

This would require partnerships with payment processors and terminal manufacturers to access transaction data. The business model could involve charging merchants a small fee per transaction for digital receipt delivery as an alternative to printing paper receipts saving them paper costs and providing environmental benefits. Consumers would benefit from never losing receipts and having all transaction data automatically organized. The NFC integration would represent a shift from reactive receipt management uploading existing paper receipts to proactive receipt capture eliminating paper from the workflow entirely.

## 8.4 Analytics and Insights

Business intelligence features would provide value to both consumers and businesses. Consumer features might include spending analysis showing total spending by category or time period, budget tracking with alerts when spending exceeds thresholds, and trend identification showing how spending patterns change over time. Business features could include merchant analytics showing customer retention and visit frequency, receipt format analysis helping merchants optimize receipt design, and expense policy compliance for corporate users ensuring submitted expenses follow company guidelines.

The analytics implementation would require a data warehouse or OLAP database optimized for analytical queries. Receipt data would be extracted, transformed, and loaded into the warehouse periodically. Analytical queries using window functions and aggregations would calculate metrics and generate reports. Visualization using Chart.js or D3.js would display data in interactive dashboards. Machine learning models could identify anomalous transactions potentially indicating fraud or errors.

## 8.5 Accounting Software Integration

Integration with popular accounting software including QuickBooks, Xero, and FreshBooks would allow businesses to seamlessly export receipts into their bookkeeping workflows. The integration would involve developing OAuth integrations for each accounting platform allowing ReTouch to access user accounts, mapping ReTouch receipt data to accounting platform concepts like expenses and accounts, implementing bulk export allowing users to select multiple receipts and push them to accounting software, and maintaining synchronization where changes in ReTouch automatically update the corresponding records in accounting software.

This integration would position ReTouch as part of the business finance stack rather than a standalone receipt manager. The value proposition to businesses would emphasize time savings from automated bookkeeping and reduced errors from manual data entry. Freemium business users might be converted to paid plans to unlock accounting integrations.

## 8.6 Microservices Expansion

The current architecture could be extended with additional microservices handling specific responsibilities. An OCR service would handle image processing independently of the main API allowing it to scale separately based on OCR workload. A notification service would send email or push notifications for events like expense report approvals or spending alerts using message queues to decouple notification generation from delivery. A search service using Elasticsearch would provide full-text search across receipt data enabling queries like finding all receipts mentioning a specific product.

These microservices would communicate through well-defined APIs or message queues. Service discovery could be implemented using Consul or Kubernetes services allowing services to locate each other dynamically. The microservices architecture would enable independent scaling where the OCR service could run on GPU instances for faster processing while API services run on standard CPU instances. Team structure could also map to services allowing specialized developers to own specific services.

## 8.7 Database Optimization

As data volume grows, database optimizations will become necessary. Read replicas would distribute query load across multiple PostgreSQL instances with writes going to the primary and reads load balanced across replicas. Redis caching would store frequently accessed data like recent receipts in memory reducing database load. Table partitioning would split large tables like receipts into smaller pieces based on date ranges or device ID improving query performance. Query optimization including adding indexes on frequently queried columns and analyzing query plans to identify bottlenecks would maintain performance as data scales.

The optimization process would involve monitoring query performance using PostgreSQL's pg_stat_statements extension to identify slow queries, profiling application code to find database hotspots, load testing to simulate high traffic scenarios, and capacity planning to predict when additional resources are needed. Database maintenance including vacuuming to reclaim space and reindexing to maintain index efficiency would be automated.

## 8.8 Multi-Region Deployment

Expanding to multiple AWS regions would improve latency for global users and provide disaster recovery capabilities. A multi-region deployment would involve replicating databases across regions using PostgreSQL replication or AWS RDS multi-region features, deploying application containers to multiple regions behind a global load balancer routing users to the nearest region, replicating S3 data across regions ensuring receipt files are available even if one region fails, and implementing active-active or active-passive failover allowing automatic recovery from regional outages.

The complexity of multi-region deployment includes handling data consistency where updates in one region must propagate to others, routing users consistently to avoid user experiencing different application states when their requests hit different regions, and managing costs since running infrastructure in multiple regions increases expenses. These tradeoffs would be evaluated based on user distribution and business requirements.
