# 2. Implementation and Technical Details

## 2.1 System Architecture

ReTouch follows a modern microservices architecture with clear separation of concerns between different functional areas of the system. The architecture has been designed to be scalable, maintainable, and secure, with each component serving a specific purpose and communicating with other components through well-defined interfaces.

### High-Level Architecture Overview

The system can be visualized as a layered architecture where user requests flow through multiple tiers before reaching the data layer and returning responses. At the outermost layer, the Internet serves as the entry point for all user traffic whether from web browsers, mobile devices, or API clients. All traffic first encounters the nginx reverse proxy which listens on port 443 for HTTPS connections. This nginx instance serves multiple critical functions including SSL and TLS termination where encrypted connections are decrypted and validated, rate limiting where requests are throttled based on predefined limits to prevent abuse, and reverse proxying where requests are routed to appropriate backend services based on URL patterns.

The architecture consists of several distinct layers that work together to provide the complete functionality. The presentation layer is handled by the React frontend application which renders the user interface and manages user interactions. The API gateway layer is implemented by nginx which routes requests, enforces security policies, and manages SSL termination. The application layer contains the business logic split across two Flask applications: the main backend service and the certificate authority service. The data layer consists of PostgreSQL databases for structured data and AWS S3 for unstructured file storage.

Behind the nginx layer sit three primary application services each serving distinct purposes. The frontend service built with React runs on port 80 within its container and serves the static files that make up the user interface. In the optimized production configuration, these static files are served directly by nginx without proxying to the React container, but the architecture supports both direct serving and proxying for flexibility during development. The backend service built with Flask runs on port 5000 and handles all business logic related to receipt management including upload, retrieval, status management, and integration with external services. The ReTouch Certificate Authority service also built with Flask runs on port 5001 and handles all certificate lifecycle operations including CSR processing, certificate issuance, and revocation management.

### Data Layer Architecture

The data layer consists of two separate PostgreSQL database instances ensuring isolation between different domains of the system. The main database stores all receipt metadata including receipt identifiers which are UUIDs providing global uniqueness and preventing enumeration attacks, device identifiers which track which device owns each receipt, creation timestamps recording when receipts were added to the system, MIME types indicating the file format of each receipt, and upload status information tracking the lifecycle state of each receipt from pending through completed or failed. It also stores device information for tracking purposes including device identifiers, creation timestamps, and receipt counts enabling analytics and quota enforcement.

The Certificate Authority database maintains its own separate data including user accounts for CA portal access with usernames and hashed passwords following security best practices, and certificate records tracking all issued certificates with their serial numbers, issuance dates, expiration dates, and revocation status. This separation ensures that compromise of one database does not automatically compromise the other and allows independent scaling and optimization of each database based on its specific access patterns and performance requirements.

For file storage, ReTouch leverages AWS S3 which provides highly durable and scalable object storage with eleven nines of durability. Receipt images in formats like JPEG and PNG, as well as PDF files, are stored in S3 organized by device identifier with each receipt file named using its unique receipt identifier. This organizational structure allows efficient listing of all receipts for a given device while maintaining global uniqueness of receipt identifiers. The backend service interacts with S3 through the boto3 Python SDK which provides a high-level interface to AWS services. The backend generates presigned URLs that allow direct browser-to-S3 file transfers without proxying large files through the application servers, significantly reducing bandwidth requirements and improving performance.

### Request Routing and Flow

The nginx reverse proxy implements sophisticated routing logic to direct traffic appropriately. When a request arrives at the nginx layer, the path is examined to determine the destination service and appropriate handling. Requests to paths beginning with /api are routed to the backend Flask service on port 5000 after first verifying that the request includes a valid client certificate signed by the ReTouch Certificate Authority. This ensures that only authorized devices can access the API endpoints that manage receipt data. The verification happens at the nginx level using the ssl_verify_client directive, which checks the certificate against the trusted CA bundle and verifies that the certificate has not expired and was properly signed.

Requests to paths beginning with /certmanage are routed to the Certificate Authority service on port 5001 where traditional session-based authentication is used instead of client certificates. This is necessary because users accessing the CA portal to request new certificates obviously do not yet have certificates to present. The CA portal uses Flask-Login for session management with secure password hashing via Werkzeug's security utilities.

Requests to /receipt-raw are also routed to the backend service but without requiring client certificate authentication. This endpoint provides an HTML view of receipts suitable for sharing via simple URLs. While less secure than the API endpoints, this allows users to share receipts with others who may not have certificates installed, which is useful for expense reporting and similar workflows.

All other requests are served as static files from the nginx document root which contains the built React application assets. These assets include the index.html file which serves as the entry point for the single-page application, JavaScript bundle files containing the compiled and minified React code, CSS files with all styling information, and image assets including logos and icons. Nginx serves these files extremely efficiently using sendfile system calls and can handle tens of thousands of concurrent static file requests with minimal CPU and memory overhead.

### Architectural Patterns

The architecture implements several important patterns that contribute to its robustness and scalability. The microservices pattern allows services to be independently deployable meaning that updates to the frontend do not require backend restarts and vice versa. Each service can have its own database following the database-per-service pattern which prevents tight coupling between services and allows independent schema evolution. Services can also scale independently based on their specific resource requirements and traffic patterns. For example, if the frontend experiences high traffic but the backend load remains moderate, additional frontend containers can be deployed without scaling the backend.

The API gateway pattern is implemented through nginx which serves as a single entry point for all requests. This provides centralized authentication where certificate verification happens once at the gateway rather than being replicated in each service, centralized rate limiting where abuse prevention is enforced consistently across all services, centralized logging where all requests are logged with consistent formatting, and simplified client configuration where clients only need to know about the gateway address rather than individual service addresses.

The Backend for Frontend pattern is evident in how the backend API has been designed specifically to meet the needs of the web frontend. The data structures returned by API endpoints match what the frontend components expect, minimizing transformation logic in the browser. For example, the receipt API returns timestamp strings in ISO 8601 format which JavaScript can parse natively, rather than Unix timestamps which would require conversion. Presigned URLs are generated by the backend but consumed directly by the frontend allowing efficient file downloads without backend proxying. This pattern optimizes the data flow and reduces unnecessary backend processing.

The repository pattern has been implemented in the backend where all database operations are abstracted through utility functions in the components/utils.py module. Business logic code in the API route handlers calls functions like create_receipt, get_receipt_from_db, and update_receipt_status without needing to know the details of SQL queries or ORM operations. This abstraction provides clean separation between business logic and data access, makes the code easier to test since database operations can be mocked, and makes it possible to swap database implementations if needed without changing business logic code.

### Data Flow Patterns

Data flows through the system following well-defined paths optimized for each operation type. When a user uploads a receipt, the flow begins with the frontend constructing a multipart form POST request containing the receipt file and associated metadata including device identifier and MIME type. This request is sent to nginx which verifies the client certificate and routes the request to the backend API. The backend creates a new receipt record in PostgreSQL with status initially set to PENDING if using presigned URLs or COMPLETED if doing direct upload. For direct uploads, the backend then uploads the file to S3 using the boto3 SDK with the device identifier and receipt identifier forming the S3 object key. The upload includes metadata such as Content-Type headers ensuring browsers handle downloads correctly. The backend then returns receipt metadata to the frontend including the receipt identifier, creation timestamp, and a presigned URL for immediate viewing if desired.

When a user retrieves a receipt, the flow is optimized to reduce backend load and minimize latency. The frontend requests receipt data from the backend API specifying both device identifier and receipt identifier in the query parameters. The backend first verifies ownership by querying PostgreSQL to ensure the receipt exists and belongs to the requesting device. This is critical for security as it prevents one device from accessing another device's receipts even if they guess or enumerate receipt identifiers. If ownership is confirmed, the backend generates a presigned S3 URL valid for one hour using S3's generate_presigned_url API. This URL allows the frontend to download the receipt image directly from S3 without further backend involvement. The presigned URL includes cryptographic signatures ensuring it cannot be tampered with and automatically expires after the configured time period. The frontend then downloads the receipt image directly from S3 using the presigned URL, and S3 serves the file with appropriate caching headers allowing browsers to cache the image locally.

The client certificate authentication flow adds an additional security layer that executes before requests reach application code. When a user makes an API request, the browser automatically includes the client certificate in the TLS handshake as part of the SSL negotiation. Nginx verifies this certificate against the trusted Certificate Authority bundle which contains the public certificate of the ReTouch CA. The verification checks that the certificate was signed by the trusted CA using proper cryptographic signatures, that the certificate has not expired based on its notBefore and notAfter dates, and that the certificate chain is valid with all intermediate certificates properly signed. If verification succeeds, nginx sets special headers like X-SSL-Client-Verify with value SUCCESS and proxies the request to the backend. If verification fails, nginx returns a 403 Forbidden response without ever reaching the backend, protecting backend resources from unauthorized access. This approach offloads cryptographic verification to nginx which is highly optimized for such operations and prevents unauthenticated requests from consuming backend resources.

### Architectural Benefits

This architectural approach provides numerous benefits that justify the additional complexity compared to a monolithic design. The system can scale horizontally by adding more instances of services behind load balancers. For example, multiple backend containers can run behind nginx with requests distributed using round-robin or least-connections algorithms. Multiple authentication layers provide defense in depth where even if one security mechanism fails, others remain in place providing continued protection. For instance, even if client certificate verification were somehow bypassed, the backend still validates device ownership before returning receipt data.

Static files are served directly by nginx which is extremely efficient compared to application server processing. Nginx uses sendfile system calls that allow the kernel to transfer file data directly from disk to network without copying through user space, and can handle tens of thousands of concurrent connections with minimal memory overhead. The clear separation of concerns makes the codebase more maintainable as developers can work on different services without conflicts or coordination overhead. Database persistence ensures data survives container restarts and node failures, with Docker volumes providing durable storage that persists across container lifecycle events. PostgreSQL's ACID guarantees ensure data consistency even in the face of crashes or network partitions.
