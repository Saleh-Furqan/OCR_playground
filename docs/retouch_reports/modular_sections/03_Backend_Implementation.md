# 3. Backend Implementation

## 3.1 Flask Application Structure

The backend follows Flask's application factory pattern where the create_app function constructs and configures the Flask application instance rather than creating a global app object at module level. This pattern provides several benefits including easier testing since tests can create isolated application instances with different configurations, support for multiple application instances running simultaneously, and cleaner dependency injection. The app.py file defines the create_app function which initializes Flask, configures the database connection, registers blueprints, and sets up error handlers.

The application structure separates concerns into distinct modules within the components package. The models.py module defines SQLAlchemy ORM models representing database tables. The utils.py module contains helper functions for common operations including database queries and S3 interactions. The api package contains route handlers for the RESTful API exposed to clients. The receipt package contains routes for public receipt viewing that do not require authentication. This modular organization makes the codebase easier to navigate as related functionality is grouped together, and allows importing only needed modules reducing coupling between different parts of the system.

Configuration management uses environment variables read through Python's os.environ dictionary. Critical configuration including database URLs, AWS credentials, and S3 bucket names are provided as environment variables rather than hardcoded in source files. This follows twelve-factor app principles separating configuration from code and allowing the same codebase to run in different environments including local development, staging, and production without modification. The Docker Compose file sets appropriate environment variables for each service ensuring each container receives its required configuration.

## 3.2 Database Models

The Receipt model represents individual receipt records stored in the PostgreSQL database. Each receipt has several attributes including receipt_id which is the primary key using UUID type ensuring global uniqueness, device_id which is a string identifying the device that owns this receipt, timestamp which records when the receipt was created using Python's datetime type, mime_type which indicates the file format like image/jpeg or application/pdf, and upload_status which tracks the current state using an enum.

The UploadStatus enum defines four possible states for receipts. NOT_UPLOADED indicates the receipt record exists but the file has not yet been uploaded to S3. PENDING indicates an upload is in progress. COMPLETED indicates the file has been successfully uploaded and is available for retrieval. FAILED indicates an upload error occurred and the file is not available. This status tracking allows the system to distinguish between different failure modes and potentially retry failed uploads or clean up stale pending records.

The Device model tracks devices that have been issued client certificates and are authorized to use the system. Each device record includes device_id which serves as the primary key and matches the Common Name in the client certificate, timestamp recording when the device was first registered, and receipt_count which is an integer tracking how many receipts this device has uploaded. The receipt count is incremented each time a receipt is created and provides a simple analytics metric. In the future this field could support quota enforcement limiting users to a certain number of receipts in free tier accounts.

SQLAlchemy's declarative base provides the foundation for these models. Classes inherit from db.Model where db is the SQLAlchemy instance, and class attributes define table columns using types like db.String, db.DateTime, and db.Integer. The __tablename__ attribute specifies the database table name, and db.Column objects define column properties including types, constraints, and default values. The nullable parameter controls whether NULL values are permitted, and default parameters specify values for columns when inserting new rows.

The models also define relationships between tables although currently ReTouch uses a simple schema without foreign key constraints. The device_id in the Receipt table conceptually relates to device_id in the Device table creating a one-to-many relationship where each device can have many receipts. However, this relationship is not enforced at the database level through foreign keys, which provides flexibility if receipts need to outlive device records or if the relationship becomes more complex in the future.

## 3.3 API Endpoints

The API is organized as a Flask-Smorest blueprint defined in components/api/routes.py. Blueprints allow grouping related routes under a common URL prefix, in this case /api, and enable modular registration of route handlers. The blueprint is registered with the Flask application in app.py using app.register_blueprint which makes all routes defined in the blueprint available at runtime.

The POST /api/receipt endpoint handles receipt creation accepting multipart form data containing the receipt file and metadata. The route handler is decorated with @blueprint.route specifying the URL path and HTTP method, and @blueprint.arguments decorating specifies a Marshmallow schema for request validation. When a request arrives, Flask-Smorest automatically deserializes the request body according to the schema and passes the validated data to the route handler as a parameter. The handler extracts the device ID from the client certificate which nginx has verified and passed via headers, generates a unique receipt ID using Python's uuid4 function, uploads the file to S3 using upload_fileobj from utils, creates a new Receipt record in PostgreSQL with status COMPLETED, increments the device's receipt count, commits the database transaction, and returns the receipt metadata as JSON with 201 Created status.

The GET /api/receipt endpoint retrieves metadata for a specific receipt accepting device_id and receipt_id as query parameters. The route handler validates that both parameters are present returning 400 Bad Request if either is missing, queries PostgreSQL for the receipt record filtering by both device ID and receipt ID, returns 404 Not Found if no matching receipt exists which prevents enumeration of receipt IDs, verifies the receipt belongs to the requesting device by comparing device IDs returning 403 Forbidden if there is a mismatch, generates a presigned S3 URL valid for one hour using generate_presigned_url from utils, and returns a JSON object containing receipt metadata and the presigned URL.

The PUT /api/receipt endpoint updates receipt status accepting device_id, receipt_id, and new status as JSON body parameters. This endpoint is currently used primarily for updating status from PENDING to COMPLETED for the presigned URL upload flow where clients first create a receipt record with PENDING status, upload the file to S3 using a presigned PUT URL, and then call this endpoint to mark the upload as COMPLETED. The handler validates ownership before allowing status updates ensuring one device cannot modify another device's receipt status.

The DELETE /api/receipt endpoint handles receipt deletion accepting device_id and receipt_id as query parameters. The handler verifies the receipt exists and belongs to the requesting device using the same ownership validation as the GET endpoint, deletes the file from S3 by calling boto3's delete_object method with the bucket name and object key, deletes the receipt record from PostgreSQL using SQLAlchemy's session.delete method, commits the transaction, and returns 204 No Content indicating successful deletion. This two-phase deletion ensures both the file and metadata are removed although there is no transaction spanning S3 and PostgreSQL so a failure after deleting from S3 but before deleting from PostgreSQL could leave orphaned database records.

The POST /api/receipt/presigned_upload endpoint generates presigned URLs for client-side uploads. This endpoint creates a new receipt record with status PENDING, generates a presigned PUT URL that allows the client to upload directly to S3, and returns both the receipt ID and presigned URL to the client. The client can then use the presigned URL to upload the file and subsequently call the status update endpoint to mark the upload as completed. This flow reduces backend bandwidth requirements as large receipt images upload directly to S3 without transiting through the backend servers.

## 3.4 Request Validation

Marshmallow schemas define the structure and validation rules for request and response data. The ReceiptSchema class defines fields including receipt_id which is a UUID field, device_id which is a String field with maximum length of 256 characters, timestamp which is a DateTime field automatically serializing Python datetime objects to ISO 8601 strings, mime_type which is a String field, and upload_status which is a String field with validation ensuring it matches one of the UploadStatus enum values.

Flask-Smorest integrates Marshmallow schemas with route handlers using decorators. The @blueprint.arguments decorator specifies a schema to use for deserializing and validating request data, automatically parsing JSON request bodies or form data according to the schema and passing the validated data dictionary to the route handler. If validation fails, Flask-Smorest automatically returns a 400 Bad Request response with details about validation errors without the route handler being called. This centralizes validation logic in schemas rather than having validation code scattered throughout route handlers.

The @blueprint.response decorator specifies a schema for serializing response data. Route handlers return Python objects including dictionaries or ORM model instances, and Flask-Smorest automatically serializes these according to the specified schema converting Python types to JSON-compatible representations. This ensures consistent response formatting across all endpoints and documents the expected response structure for API consumers.

## 3.5 S3 Integration

The backend integrates with AWS S3 through boto3 which is the official AWS SDK for Python. The utils.py module initializes a boto3 S3 client using credentials from environment variables including AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY. These credentials are configured in the AWS IAM console with permissions limited to the specific S3 bucket used by ReTouch following the principle of least privilege.

The upload_fileobj function accepts a file-like object and an S3 key, and uploads the file to the configured bucket. It uses the S3 client's upload_fileobj method which handles multipart uploads automatically for large files. The function sets appropriate metadata including Content-Type headers based on the MIME type ensuring browsers handle downloads correctly. The S3 key is constructed as device_id/receipt_id allowing efficient listing of all receipts for a specific device using S3's prefix-based listing.

The generate_presigned_url function creates time-limited URLs for file access without exposing AWS credentials to clients. It uses the S3 client's generate_presigned_url method specifying the HTTP method, bucket name, object key, and expiration time. The returned URL includes query parameters containing a signature computed using the AWS secret key. When a client requests the URL, S3 validates the signature ensuring the URL has not been tampered with and that it has not expired. The presigned URL allows clients to download receipt images directly from S3 without making requests through the backend, significantly reducing backend bandwidth and latency.

The get_receipt_s3_url helper function combines receipt ID and device ID to construct the S3 object key following the device_id/receipt_id pattern. This function is used throughout the codebase to ensure consistent key formatting preventing errors where different parts of the system use different key structures.

## 3.6 Database Operations

Database operations use SQLAlchemy's session object which manages the connection pool and transaction boundaries. The session is obtained from db.session where db is the SQLAlchemy instance created in the application factory. The session provides methods including query for retrieving records, add for inserting new records, delete for removing records, and commit for persisting changes to the database.

The create_receipt utility function encapsulates receipt creation logic accepting parameters including receipt ID, device ID, MIME type, and status. It creates a new Receipt model instance populating its attributes with the provided values and the current timestamp, adds the instance to the session using session.add, queries for the corresponding Device record and increments its receipt_count, commits the transaction using session.commit which persists both the new receipt and updated device count atomically, and returns the created receipt instance. The atomic commit ensures both changes succeed or both are rolled back maintaining data consistency.

The get_receipt_from_db function retrieves a receipt by device ID and receipt ID by constructing a query that filters on both fields. Using both fields in the query ensures that ownership is verified at the database level preventing one device from accessing another device's receipts even if they know the receipt ID. The filter_by method accepts keyword arguments corresponding to model attributes and adds WHERE clauses to the SQL query. The first method executes the query and returns the first matching record or None if no records match, which the route handler interprets as 404 Not Found.

The update_receipt_status function modifies the status field of an existing receipt. It first retrieves the receipt using get_receipt_from_db ensuring it exists and belongs to the requesting device, updates the upload_status attribute to the new value, and commits the transaction persisting the change. SQLAlchemy's ORM tracks modifications to model instances automatically generating appropriate UPDATE statements when the session is committed.

Transaction rollback is handled through error handlers that catch exceptions during request processing. If an exception occurs after modifying database objects but before committing, the finally block calls session.rollback which discards all pending changes and returns the session to a clean state. This prevents partial updates where some changes are committed but others are not, maintaining database consistency. The application-level transaction boundaries supplement PostgreSQL's ACID guarantees ensuring data integrity.

## 3.7 Error Handling

Flask provides error handling through the @app.errorhandler decorator which registers functions to process exceptions of specific types. The backend defines handlers for common HTTP errors including 400 Bad Request for client errors such as invalid request data, 404 Not Found for requests referencing nonexistent resources, 403 Forbidden for authorization failures where the client is authenticated but not permitted to access the requested resource, and 500 Internal Server Error for unexpected exceptions.

Each error handler returns a JSON object containing an error code, message, and optionally additional details about the error. This structured error format allows frontend code to display appropriate error messages to users rather than exposing raw exception messages which could leak sensitive information. The handlers also log errors using Python's logging module ensuring error details are captured for debugging without exposing them to clients.

Flask-Smorest provides automatic error handling for validation failures. When a request fails Marshmallow validation, Flask-Smorest returns a 400 response with a JSON object describing which fields failed validation and why. This immediate feedback helps API consumers correct their requests without needing to understand backend code or inspect logs.

## 3.8 Production Deployment

The backend runs in production using Gunicorn as the WSGI server. The wsgi.py file creates the application instance by calling the create_app factory function and exposes it as a module-level app variable that Gunicorn can import. The docker-compose.yml file configures the backend container to run Gunicorn with the command gunicorn --bind 0.0.0.0:5000 --workers 4 wsgi:app which binds to all interfaces on port 5000 and spawns four worker processes.

The worker count is configured based on the available CPU cores following the formula 2 * NUM_CORES + 1. Each worker is a separate OS process handling requests independently, allowing true parallelism on multi-core systems. Gunicorn's master process monitors workers and restarts them if they crash or become unresponsive ensuring the application remains available even if individual workers encounter errors.

The wsgi-docker-entrypoint.sh script handles initialization tasks before starting Gunicorn. It runs database migrations using Alembic ensuring the database schema matches the model definitions, waits for PostgreSQL to be ready using the wait-for-it.sh utility script preventing startup errors if the database container is not yet accepting connections, and then executes Gunicorn. This entrypoint pattern ensures the container initializes properly regardless of the order in which Docker Compose starts containers.
