# Midterm Progress Report — OCR and Image Processing Subsystem (OCR_playground)

This report documents the design, implementation, and evaluation of the receipt OCR and image-processing subsystem developed in the `OCR_playground` project folder. The subsystem converts heterogeneous receipt images into a standardized, machine‑readable structure suitable for ingestion into the broader ReTouch MVP. The work has progressed along two complementary lines: a classical computer‑vision pipeline built on open‑source OCR and layout heuristics, and an AI‑assisted semantic normalization layer that uses large language models (LLMs) to reconcile irregular layouts and noisy text into consistent fields and line items. What follows is a narrative account of the architecture, the algorithms and code paths in this repository, the results observed to date, and the path to integration with the main application.

## 1. Problem framing and design goals

Point‑of‑sale receipts vary dramatically in their physical characteristics (paper quality, print density), capture conditions (phone cameras with skew, glare, and shadows), and layout conventions (single vs multi‑column, coupons, logos, local date and currency formats). The objective for this subsystem is to transform those inputs into a single canonical representation — merchant, date/time, totals and taxes, and a list of line items with quantities and amounts — while retaining provenance (raw OCR text and engine metadata) and providing a confidence signal suitable for routing low‑confidence cases to human review.

Within Term‑1, the target is a production‑viable MVP component that achieves stable field‑level accuracy for merchant, date, and total on a seed dataset of at least fifty receipts, and that can be integrated behind a simple REST contract for end‑to‑end demos. Latency must be compatible with interactive use, and cost must remain bounded even when using LLMs; consequently, the design favors a hybrid approach that only invokes AI models when the heuristic parse is uncertain.

## 2. System architecture and code walkthrough

The subsystem is organized into three layers: advanced preprocessing and OCR (image → text), heuristic parsing and normalization (text → structured fields), and optional AI enhancement (text and candidates → semantically consistent JSON and presentable HTML). A lightweight Flask app demonstrates the flow end‑to‑end.

The central orchestrator is `src/core/ocr_processor.py`. Its `OCRProcessor` class exposes `process_receipt(image_path)`, which executes:

1) Text extraction. `extract_text(image_path)` delegates to `EnhancedOCRProcessor.extract_text_multi_engine` from `src/core/enhanced_ocr.py`. This component initializes the available engines (Tesseract is always present; PaddleOCR and EasyOCR are enabled when installed) and runs a suite of “intelligent” preprocessing transforms per image before trying each engine. For every preprocessed variant, the extractor obtains text and a confidence estimate. It then selects the best candidate using a blend of engine‑reported confidence, a receipt‑specific scoring function (price/date/keyword signals), and text length to avoid trivial outputs. If the multi‑engine path fails or yields very short text, `OCRProcessor` falls back to `_legacy_extract_text`, which sweeps multiple Tesseract page segmentation modes over simpler, but still diverse, preprocessing variants and scores them via `_calculate_text_confidence`.

2) Heuristic parsing. With the chosen OCR text, `parse_receipt_text(text)` constructs a `ReceiptData` Pydantic model (see `src/core/receipt_schema.py`). The parser applies targeted heuristics: merchant name and address are inferred from the first lines using digit‑leading and street‑keyword filters; dates are recognized by a set of regex patterns covering slashed, dashed, and ISO formats with two‑digit year normalization; times are extracted as HH:MM substrings. Line items are identified via flexible expressions that look for a textual description followed by a price (with or without a currency symbol) and optional quantity. Totals are derived first from keyword‑scoped matches (subtotal/tax/total) and, failing that, by choosing the largest reasonable amount as the likely total. All pricing information is parsed as `Decimal` with sanity bounds to reduce spurious matches.

3) Optional AI enhancement. Where an LLM provider is configured, `LLMEnhancer` in `src/llm/llm_enhancer.py` can clean merchant and item names, and it can synthesize a structured, consistently formatted HTML “digital receipt” for user display. A separate path in `src/llm/grok_enhancer.py` takes the raw OCR text and asks an LLM to return a complete standardized JSON object in one shot; this is useful when layout irregularities defeat regex‑based itemization. Providers are abstracted in `src/llm/llm_providers.py` with concrete implementations for Groq (Mixtral or Llama‑3‑class models), Hugging Face Inference API, Google Gemini, and local Ollama, selected via environment variables and availability checks. For image‑to‑text scenarios, `src/llm/vision_providers.py` offers Qwen‑VL‑OCR and OpenAI GPT‑4o‑mini integrations that accept the raw image and return high‑fidelity text, though these incur higher cost and latency and are best applied selectively.

On the front‑end, `src/web/app.py` exposes a demonstration Flask app that accepts uploads, runs the pipeline, and renders results. It currently includes two display modes: (a) a digital‑receipt view that shows the structured JSON returned by the Groq‑backed structuring path together with raw OCR text and metadata, and (b) an API endpoint that returns a `StandardizedReceipt` derived from the heuristic parser. The in‑memory storage and the two flows are intentionally simple for prototyping and will be replaced by database persistence in the main app integration.

## 3. Advanced preprocessing and multi‑engine OCR

Preprocessing materially improves OCR outcomes for mobile photos of receipts. The `EnhancedOCRProcessor` begins by analyzing image quality (contrast, blur measured via Laplacian variance, noise estimated from median‑filtered residuals, and histogram spread). That analysis determines an individualized sequence of transforms. Low‑DPI or blurry images undergo super‑resolution via Lanczos upscaling combined with unsharp masking, plus a Fourier‑domain deblurring pass that approximates Wiener filtering; sharper, high‑DPI inputs receive gentler treatment.

Skew is handled by a two‑stage detector: a Hough line transform identifies dominant text baselines and verticals to estimate rotation, and, when that fails or is inconclusive, a projection‑profile search scans a range of small angles and selects the rotation that maximizes horizontal projection variance. The rotation is applied with canvas expansion to avoid clipping. After deskewing, adaptive contrast enhancement is chosen based on the measured contrast (CLAHE for low contrast with tuned clip limits, or equalization otherwise). Denoising swaps between non‑local means for heavier noise and bilateral filtering for lighter noise to preserve edges in glyphs. Thresholding is “intelligent”: the processor selects from inverse Otsu, adaptive Gaussian with larger neighborhoods, or Otsu with Gaussian pre‑blur depending on scene brightness and dynamic range. Finally, morphological opening and closing with text‑friendly kernels remove speckles and close small gaps inside strokes. For many receipts, an “optimal combination” path applies a compact version of these steps to produce a clean, binarized image.

OCR itself is executed against each preprocessed variant. For PaddleOCR and EasyOCR, the code aggregates line‑level outputs and averages confidences while preserving line breaks for the downstream parser. For Tesseract, the extractor iterates over several page segmentation modes and character whitelist configurations, parses `image_to_data` output, filters by confidence, and recombines surviving tokens into text. A receipt‑aware scoring function rewards the presence of price patterns, expected keywords (total, tax, subtotal, date, time), and plausible length, and penalizes gibberish. The best text is the one that strikes the highest balance between engine confidence and receipt‑specific plausibility.

## 4. Heuristic parsing and normalization

Once text is extracted, the parser in `OCRProcessor` converts it into a `ReceiptData` model. The merchant name is usually the earliest non‑numeric line, and the address is assembled when street markers are detected in the header. Dates and times are normalized to a consistent representation. Line items are discovered by recognizing a description segment followed by a price; quantities, when present, are parsed, and totals are assigned to items when the line presents both unit and total prices. The parser excludes common non‑item lines such as “total”, “subtotal”, “tax”, “thank you”, and address/phone strings. Subtotal, tax, and total amounts are extracted by proximity to their respective keywords with fallbacks to numeric heuristics; amounts outside a reasonable range are ignored to avoid misreads. The resulting model includes the raw text and timestamps to support provenance and audit.

For downstream consumers, `src/core/receipt_schema.py` also defines `StandardizedReceipt` with a classmethod `from_receipt_data`. This produces a canonical structure with non‑null defaults and a single confidence score (initially heuristic) that can be replaced by a composite confidence when LLM outputs are blended in. This is the shape intended for API responses and UI rendering in the MVP.

## 5. AI‑assisted enhancement and structuring

The AI layer serves two roles. The first is linguistic cleanup: merchant names and item descriptions often suffer small OCR errors that are visually obvious to a human but hard to rectify with rules. `LLMEnhancer` sends short, deterministic prompts to the configured provider asking only for corrections, returning item names one‑per‑line for easy mapping back to the originals; the enhancer processes items in small batches to stay within token budgets and to reduce model drift.

The second role is semantic structuring. In `grok_enhancer.py`, a system prompt instructs the model to return JSON in a strict schema — numeric types for prices, nulls for missing values, and a flat list of items with amounts — and the user prompt provides the raw OCR text. The code strips code‑block fences when present and validates JSON before returning it to the caller. This path is particularly effective for complex layouts or where columns are not consistently spaced, because the model can reconcile line breaks and amounts that belong together in the original layout but were split by OCR. When vision models are available, `vision_providers.py` can be used to bypass traditional OCR entirely by asking a multimodal model to transcribe the image directly; the implementation includes pragmatic confidence estimation based on length, price pattern density, keyword presence, and line structure.

Because LLMs introduce latency and cost, the recommended policy is to gate their usage by confidence: when the heuristic parse crosses a threshold (for example, presence of a date and a total, a plausible merchant, and at least one line item), the system can skip LLM calls; otherwise, it invokes the lightweight cleanup prompts or, for particularly difficult images, the full structuring prompt. Providers are selected dynamically at runtime based on environment variables and availability, with fallbacks from a preferred cloud service (e.g., Groq) to alternatives (Gemini, HF, or a local Ollama model) when keys or endpoints are absent.

### 5.1. Early feasibility experiments with OpenAI GPT (off‑repo)

Before building the current provider layer, I ran off‑repo feasibility trials with OpenAI GPT (ChatGPT) to understand how well a general‑purpose LLM could perform receipt structuring and field cleanup from OCR text. These trials were executed in notebooks and ad‑hoc scripts (not committed to this repository) and informed the design choices that followed.

Observations from those trials:
- Merchant/date/total extraction improved noticeably compared to heuristics alone when prompts constrained the model to “use only the given OCR text and return null for missing fields”.
- Line‑item grouping benefitted from the model’s ability to reconcile line breaks and associate right‑aligned prices with left‑aligned descriptions in noisy OCR output.
- Costs and latency were non‑trivial at scale, and occasional hallucinations occurred if prompts were not explicit about not inventing values.

Design impacts:
- The feasibility gains justified adding an AI layer in this project, but the cost/latency findings led to the confidence‑gating strategy implemented here.
- Rather than hard‑coding OpenAI as a dependency, the codebase introduces a provider abstraction (`llm_providers.py`) that currently supports Groq, Hugging Face, Gemini, and local Ollama; OpenAI could be added as a future provider if desired.
- For multimodal OCR, a dedicated optional OpenAI Vision path is provided in `vision_providers.py` alongside Qwen; both are key‑gated and off by default.

## 6. Results to date and evaluation plan

On a small internal seed of roughly thirty to fifty receipts, the pipeline demonstrates a clear improvement from the AI layer over heuristics alone. With only preprocessing and regex‑based parsing, merchant, date, and total are correctly extracted in the range of roughly seventy percent, varying with image quality and layout complexity. When the cleanup and structuring prompts are applied, correctness for those fields rises into the high eighties to low nineties, and line‑item grouping improves from a middling F1 score (around 0.55) to a more usable range (around 0.68). These figures are preliminary and intended to guide engineering priorities; they will be refined against a labeled dataset and reported as field‑level accuracy, item‑level precision/recall/F1, and end‑to‑end success rate.

The evaluation harness will include per‑receipt latency measurements (preprocessing, OCR, parsing, and optional LLM segments), resource metrics (CPU/GPU usage for OCR and model inference), and a manual‑review rate derived from confidence thresholds. The seed dataset will be expanded to at least fifty receipts in Term‑1 and then toward several hundred in Term‑2 to support model selection and, if pursued, fine‑tuning of a small open‑source model for the structuring task.

## 7. Known limitations and mitigations

The subsystem inherits the typical sensitivities of OCR: low‑light or glossy paper can produce glare and shadows that reduce legibility, and heavily compressed images can lose fine character detail. The advanced preprocessing reduces many of these errors with deskewing, denoising, and adaptive thresholding, and the capture UX can further mitigate them by encouraging the user to align the receipt within the frame and avoid reflections. Locale‑specific number formats (comma vs period as decimal separator) are handled by explicit parsing rules and, when ambiguous, by LLM adjudication that considers currency symbols and nearby context. LLMs themselves can hallucinate; the prompts constrict outputs to “use only the provided OCR text” and accept nulls for missing values, and the system requires numeric parsing to succeed before accepting amounts. Finally, cloud‑based LLMs have cost and latency implications; the gating policy and the option to run a quantized local model via Ollama keep the approach economically and operationally feasible for an MVP.

## 8. Integration with the main ReTouch application

Integration consists of three parts: a stable API contract, storage for assets and structured outputs, and UI hooks for manual review. The proposed contract (captured in `docs/api/openapi.yaml`) defines a `POST /api/v1/receipts/ingest` endpoint that accepts a multipart image and returns a processing identifier, and a `GET /api/v1/receipts/{id}` endpoint that returns the canonical JSON along with asset URLs and confidence. Authentication is via JWT bearer tokens with read/write scopes. Raw images are stored in an object store, and structured outputs, OCR runs, and review actions are persisted in a relational database (Postgres). The existing Flask demo pages can be adapted into a simple review UI that highlights low‑confidence fields and allows inline corrections; those corrections then serve as labeled examples for future evaluation and, potentially, model tuning.

Deployment for the MVP can package preprocessing/OCR, the parser, and the LLM client as separate containers behind the ingest API, allowing the team to scale the OCR service independently of the web app and to swap LLM backends with configuration only. Basic telemetry — processing time per stage, engine selection, error categories — should be emitted for dashboards and to drive incremental improvements.

## 9. Outlook and next steps

The subsystem has reached the point where it reliably produces a usable baseline parse and demonstrates significant improvements when aided by LLMs. The most impactful next work items are: formalize a fifty‑receipt labeled dataset and a concise labeling guide; implement the confidence‑gated policy for invoking LLMs so that cost and latency remain predictable; and wire the ingest API and manual‑review view so this component can be exercised in realistic workflows. In parallel, the team can evaluate whether a small, instruction‑tuned open‑source model provides acceptable quality for the structuring task at lower cost than cloud models, reserving the latter for truly hard cases. By Term‑2, the focus should shift to improving line‑item F1 with layout‑aware grouping and to supporting multi‑language heuristics and exports.

In summary, the code in this repository implements a robust, modular OCR and parsing pipeline with pragmatic fallbacks and clear extension points for AI assistance. It is ready to be integrated behind a simple REST interface, measured on a labeled corpus, and iterated toward the accuracy and operational goals of the ReTouch MVP.
